# Decisions

Settled questions, backfilled from v0.1's dated amendments and this project's
conversation history. **Read before proposing an alternative** — the rejected options
are recorded so nobody re-argues them.

This file never overrides a spec file. It explains. If it contradicts one, one of them
is stale — flag it rather than picking.

---

## D1 · Per-file contents API, not the tarball endpoint

**Decision:** fetch selected files individually via the GitHub contents API.

**Reasoning:** per-file HTTP status is load-bearing for `selected == read + failed +
not_fetched` (CONTRACT I-1). Under a tarball, a file that could not be read is
indistinguishable from one that decoded badly.

**Rejected:** *tarball/zipball* — one call instead of 11,215 for a large repo, but it
downloads everything to read a subset (~1 GB of kubernetes to read 8,376 files),
loses per-file error granularity, and drags in archive handling, temp disk and
decompression-bomb limits. Its only advantage evaporates once a read cap exists:
capped, the per-file path costs at most `cap + 2` calls regardless of repo size.

**Would reopen if:** the cap is removed, or repos routinely exceed what per-file
fetching can serve.

## D2 · Gemini over Groq, and Flash Lite over quality Flash

**Decision:** Google Gemini, `gemini-3.5-flash-lite` as the default model.

**Reasoning:** Groq's free tier is ~6–12K tokens/minute; a single repo-summary prompt
is ~17K. Wrong tool, not a tuning problem. Within Gemini, **requests-per-day is the
binding constraint, not tokens** — quality Flash allows 20/day, Flash Lite ~500/day at
the same tokens-per-minute. 20/day is unusable for iteration.

**Rejected:** *Groq* (throughput too low for a single request); *quality Flash*
(25× less daily budget for quality that measurement did not show mattering — a capped
`psf/requests` summary scored 4.6/5 on Flash Lite).

**Would reopen if:** summary quality proves insufficient in feedback, or an MCP
direction makes RepoBridge's own provider unnecessary.

## D3 · Free-tier training on submitted prompts — accepted, with a hard gate

**Decision:** accept that Google's free tier may use submitted prompts for training,
**only because v0.1 is public-repos-only**.

**Reasoning:** nothing is disclosed that was not already public.

**Gate — non-negotiable:** before the first private repository is read,
summarisation must move to a paid tier with training disabled, or to a different
provider. Recorded in `spec.md` as a blocking prerequisite and in `CONTRACT.md` under
"never do this".

**Would reopen if:** never in the permissive direction. Only to tighten.

## D4 · Secrets from the environment only

**Decision:** no token or key is accepted as a request field.

**Reasoning:** a per-request secret flows into persistence, diagnostics and logs by
default, and every future layer must remember to scrub it. The environment path also
matches how MCP servers conventionally receive credentials, so it is the direction
that leads somewhere.

**Rejected:** *per-request `github_token`* — the original `spec.md` §5 listed it as an
input. No such field was ever implemented, and the spec was amended (2026-08-18) to say
it is environment-only rather than the code changed to accept it.

**Rejected in the same amendment:** *per-request `llm_provider`* — "(string, optional)
Choice of LLM backend". This is the one that was genuinely accepted-in-spec and never
built; its named examples (`openrouter`, `groq`) were stale as well. Provider and model
are configuration for the same reason the token is, and are read from the environment
at call time.

## D5 · No migrations for v0.1

**Decision:** no Alembic. A schema change requires deleting the database.

**Reasoning:** every stored row derives from a public repository and regenerates by
re-running. The reset costs quota, not information. What was hardened instead is the
*failure*: a stale database now names the exact file path and the policy, rather than
throwing `OperationalError` mid-request on every endpoint.

**Rejected:** *Alembic* — a dependency plus a migration workflow nobody can exercise,
protecting data that is reproducible.

**Would reopen if:** a database holds anything that cannot be regenerated by
re-running — user annotations, private-repo results, anything with cost attached.

---

## D6 · No API version prefix

**Decision:** endpoints are unversioned, and the README says the API is unstable.

**Reasoning:** a prefix is a promise. The schema moved four times and M8 rewrote every
error body; shipping `/v1/` and then breaking it is worse than shipping nothing,
because the prefix is a claim. `test_no_endpoint_has_acquired_a_version_prefix` fails
if one appears without the README changing with it.

**Would reopen if:** an external consumer exists to pin it. The MCP server is the
likely trigger.

---

## D7 · Logs cover process facts only

**Decision:** one startup line with process facts. No per-module logging hooks.

**Reasoning:** diagnostics explain a *run*. Per-module hooks would create a second
narrative of the same run that drifts from the timeline — the exact failure
diagnostics was built to prevent.

**Rejected:** *hooks in `selection.py` / `extraction.py` / `github_client.py`* —
would require deciding what those modules log independently of the timeline, which is
a design question, not a mechanical edit.

## D8 · `/api/runs/{id}/tree` deliberately not built

**Decision:** no separate tree endpoint, despite `spec.md` §9 and `evals.md` naming
one.

**Reasoning:** the tree *is* the classified entries, and `/files` already serves them
with filtering and pagination. Two contracts for one fact is worse than one.

**Note:** the spec files still name it. Left as written, with this entry explaining
why it does not exist.

## D9 · The read cap is rank-ordered, not a prefix

**Decision:** files selected for reading are ranked — orienting docs first, shallower
paths, then a round-robin across top-level areas — rather than taken in tree order.

**Reasoning:** the `psf/requests` finding. Capped at 20 alphabetically, the summary
described an HTTP library as CI infrastructure. Every fact was grounded; the
conclusion was wrong.

**Rejected:** *reusing the chunk-ranking signals alone* — measured, and insufficient:
it still read zero source files, merely moving the concentration from `.github/` to
`docs/`. Chunk ranking orders content already read; file ranking decides what is read
at all, so an area the cap never reaches is absent from the evidence entirely.

**Would reopen if:** a better ranking signal is measured, not argued.

## D10 · Deployment is a shared demo, not multi-user

**Decision:** one instance, the operator's keys, one database visible to all
visitors, with rate limits. Recorded as Milestone 10.5.

**Reasoning:** the purpose is a feedback round. Building auth and per-user key
management before knowing whether anyone wants the product spends months on the least
differentiated work in the project.

**Rejected:** *multi-user now* — gated on someone asking to pay, or repeatedly hitting
the shared limits and asking for their own instance.

**Known consequence, accepted:** the API is unauthenticated, so anyone with the URL
can call `POST /api/analyze` directly. Rate limits apply at the endpoint; there is no
other barrier.

## D11 · Sliding-window rate limiter, not a token bucket

**Decision:** a sliding log over `deque` + `time.monotonic()`, stdlib only.

**Reasoning:** it knows when the oldest request in the window happened, so it **can
say when the limit lifts**. Every other limit in this project names its own reset; a
token bucket could only say "too many requests", which would make it the single
dishonest limit in the codebase.

---

## D12 · A daily-quota 429 is never retried

**Decision:** retry 503, 500 and per-minute 429s with bounded exponential backoff.
Never retry a **daily-quota** 429, and never retry any other 4xx.

**Reasoning:** the daily-quota 429 carries a `RetryInfo` of about **58 seconds, and it
is wrong** — the allowance does not return until the quota day rolls over, hours later.
Honouring it spends the whole retry budget against a wall it cannot clear and then fails
identically, having burned the time. It is detected from the `QuotaFailure` violation (a
`quotaId` or `quotaMetric` naming a per-day quota) and fails immediately, naming the
environment variable that switches model — which is the only recovery there is.

Other 4xx are not retried because a request the provider rejected as invalid does not
become valid by repetition: a wrong model ID 404s identically three times.

**Rejected:** *honouring the advertised delay* — measured, and it is a lie. This is the
general form: **never sleep an advertised retry delay without checking it against the
quota window it names.** Recorded in `CONTRACT.md` under "never do this".

**Would reopen if:** the provider's daily-quota errors start advertising a truthful
reset. Verify by measurement, not by reading their documentation.

## D13 · A stored run can be re-summarised

**Decision:** `POST /api/runs/{id}/summarize` regenerates a summary from stored chunks —
no GitHub call, no file re-read, provenance recomputed from the stored inventory.

**Reasoning:** without it, a run whose summary hit a 503 or an exhausted quota is dead.
The only recovery would be re-analysing the repository, spending GitHub calls to re-read
files RepoBridge already has, in order to retry the one stage that failed. Grounding is
unaffected: provenance is computed from the inventory before the first attempt, so it is
identical whichever attempt succeeds and whichever day the summary is generated.

**Known consequence, accepted:** re-summarising **overwrites**. There is no summary
history, and no test pins one — see `capabilities.md` 4.8.

## D14 · Configuration is read at call time, never bound at import

**Decision:** every environment-backed value — the read cap, the model, the token
budget, the deployment limits, the database URL — is read inside an accessor at call
time. Never in a default argument, never at module import.

**Reasoning:** a value bound at definition time cannot be changed without a restart and
cannot be tested without reaching into module internals. This is not a general
preference for configurability; it is load-bearing twice over. The provider quota is
*per model*, so switching models is the only recovery from an exhausted day, and a
recovery that needs a code edit and a restart is not a recovery.

**Rejected:** *`def f(cfg = DEFAULT_CONFIG)`* — the Milestone 5 extraction cap froze this
way once already, which is why it is now written down and tested
(`test_the_model_is_read_at_call_time_not_bound_at_import`) rather than assumed.

## D15 · Successes are not wrapped in a `data` envelope

**Decision:** errors get one envelope; successful responses are returned bare.

**Reasoning:** the errors genuinely had two incompatible shapes — ours was
`{"detail": {...}}`, FastAPI's validation failures were `{"detail": [...]}`, the same key
holding an object in one case and a list in the other. A consumer could not write one
parser. **The successes did not have that problem.** Wrapping them would re-path every
field in every consumer, every test and every template — including every honesty field
whose exact location `smoke.md` cites — to convey nothing a caller does not already know
from the status code.

**Rejected:** *`tasks.md`'s "consistent `data` and `error` fields or similar pattern"* —
this is the "similar pattern". Also rejected: keeping FastAPI's `detail` key, which is
meaningless to a consumer (detail of *what*?) and would have let a client written against
the old shape keep working for 404s and break silently on 422s.

## D16 · Four diagnostic levels, and deliberately no `WARNING`

**Decision:** `INFO`, `PARTIAL`, `DEGRADED`, `ERROR`.

**Reasoning:** three levels collapse two genuinely different outcomes into "warning" — *a
stage that finished but was bounded* (read 20 of 107) and *a stage that did not finish and
was survived* (the tree call failed). A reader scanning a timeline needs those apart: the
first needs no action, the second is why the run looks thinner than expected. Level
describes the **event's own subject, not the whole run**, so one undecodable file is
DEGRADED while the content stage that skipped past it is PARTIAL, and both are true.

**Rejected:** *a `WARNING` level* — every candidate for it is really one of PARTIAL or
DEGRADED, and **having both a precise and a vague option guarantees the vague one gets
used**. `evals.md` names "empty or vague diagnostics" as a failure signal, and a loose
level set is the fastest way to become vague. Enforced: PARTIAL must carry numbers,
DEGRADED must carry a reason.

## D17 · Directories are counted, not classified

**Decision:** a tree entry of type `tree` returns `None` from `classify_entry` and is
counted. It is stored with its own row-level status (`directory`) so the identity is
reconstructible by `GROUP BY`, but it is never SELECTED, SKIPPED or FAILED.

**Reasoning:** classification answers "will we read this file's content?", which is not a
meaningful question about a directory.

**Rejected:** *marking them SKIPPED* — it would need a skip reason that is not a real
decision mechanism, and it would inflate the skip counts with noise: "14 skipped" would
mean something different from what a human reading diagnostics assumes. The entries are
still fully accounted for, by the identity in `CONTRACT.md` I-1.

## D18 · Reopen hosted multi-user work for feasibility planning only

**Decision:** the owner request of 2026-10-17 reopens D10's multi-user gate for
scoping a future version. It does not change v0.1 or v0.2 runtime behavior, close v0.2
M0, or authorize implementation. The dated proposal is in
`specs/003-repobridge-hosted-platform/`.

**Proposed product shape:** anonymous visitors use a clearly disclosed shared demo
pool backed by operator credentials and a hard instance-wide budget. Each guest browser
session gets a short-lived logical data scope in the shared database; sharing a quota
does not make runs visible between guests. Google-signed-in users get their own logical
workspace and bring their own GitHub and Gemini keys. A workspace boundary is a
data-access boundary, not a separate database instance per person: one shared
relational store with mandatory tenant ownership is the free-hosting candidate.

**Required gates before implementation:** M0 still closes first. The platform must
then pass a zero-cost hosting and durable-storage feasibility check, and the credential
flow must receive a threat review and a narrow I-6 amendment. Until then, I-6 continues
to prohibit credentials in requests or storage.

**Quota facts to design around:** GitHub's standard authenticated REST API limit is
5,000 requests per hour per user, not 5,000 per minute or per day. Gemini limits vary
by model, project, and tier; they are applied per project, not per API key, and the
active values are shown in AI Studio. Do not encode `5 RPM` or `100 RPD` as universal
limits. Each mode needs app-side RPM and daily caps, and provider errors/headers must be
reported truthfully. See the future spec for the reviewed primary sources.

**Free-tier constraints:** Render Free Postgres expires after 30 days and has no
backups; Free web services have no persistent disk. Neon Free is the leading first
candidate for a no-cost persistence migration proof because the app uses SQLAlchemy,
but it currently has only the SQLite async driver and SQLite-specific schema-version
handling. A Postgres driver, database-layer changes, and migrations are required. Its
limits, recovery, and billing-stop behavior remain unverified for this workload.
Cloudflare D1 is an alternate with material runtime
constraints: the current maximum 102 GitHub calls exceeds the Free Worker's 50
subrequests per invocation, and the current SQLAlchemy/aiosqlite path is not a D1
binding adapter. Neither is selected. If no durable $0 store passes the feasibility
gate, stop and ask whether temporary workspaces with export are acceptable.

**Still in force:** D3's public-repository-only gate. Users' own free Gemini keys do not
remove Google's free-service data-use terms; private repositories stay out of scope
until that privacy gate is independently cleared.

## Deliberate asymmetries

*Record these, or someone will "fix" them.*

- **Extensions and config filenames are matched case-insensitively;
  `excluded_directories` is case-sensitive.** Directory names are meaningfully
  case-sensitive on Linux — `Build/` is not `build/` — and folding could over-exclude.

- **`TOO_LARGE` is checked last in the precedence order.** It therefore means "we
  would have read this, but it is too big", rather than doubling up on files already
  skipped for another reason. An oversized image reports `NON_TEXT_ASSET`, which is
  the more informative truth.

- **Truncation keeps `resolved_ref` populated** while every other tree failure nulls
  it. GitHub *did* resolve the ref; the answer is merely partial. Nulling it would be
  an over-correction — a new lie in the opposite direction.

- **`LOCKFILE` exists as a separate code even though lockfiles are valid JSON.**
  Without a name-level rule, `package-lock.json` would be SELECTED as a supported
  type and a 250 KB generated file would become "context".
